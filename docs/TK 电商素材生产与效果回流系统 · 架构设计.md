# 青帆 Qingfan · TK 电商素材生产与投放系统 · 架构设计

Oct 12, 2026 · @hon

## 产品定位与设计原则

青帆（Qingfan）定位为「爆款结构复刻 + 原创素材生产 + 投放监控 + 效果回流」：把罗盘爆款当作结构和卖点的参考，用商家自有素材和 AI 生成目标市场语言的成片，再用投放数据反过来优化下一批素材。第一批用户是印尼 TikTok Shop 运营（每人 3–4 家店），印尼语是首个上线的语言；语言和市场从第一版起就是可配置项，扩展到其他市场不改架构，验证后再开放多租户。

五条设计原则：

- **不做去重对抗。** 不提供加噪点、抖帧率、剥元数据这类规避平台检测的功能；平台检测会持续升级，产品价值不能建立在漏洞上，也会危及 TikTok API 授权。
- **不碰账号操作。** 客户端不做浏览器自动化、不模拟登录、不代发视频；与 TikTok 的交互只走官方 OAuth 接口，涉及花钱的写操作一律经过审批和限额。
- **LLM 只做决策，渲染必须确定性。** LLM 输出结构化的时间线 JSON，由 FFmpeg 按 JSON 渲染，同一份 JSON 永远渲染出同一条视频，可复现、可调试。
- **重计算在本地，数据和授权在云端。** 视频编解码放在运营电脑上省带宽和 GPU 成本；素材元数据、成片编号、效果数据、OAuth token 集中在云端。
- **每条成片从出生就可追踪。** 成片 ID 记录完整「配方」（参考爆款、钩子类型、镜头来源、配音方式），发布时绑定 TikTok 视频 ID，回流数据才能做归因。

## 总体架构

系统分三层：视频文件始终留在运营电脑上，云端只处理元数据、AI 调用和效果数据，外部只连模型供应商、抖音选品数据源和 TikTok 官方接口。

## 抖音罗盘选品数据

罗盘数据是整条链路的起点：它决定「做哪个商品」和「参考哪条爆款」，也是验证选品逻辑的另一半数据。系统在云端新增**选品数据模块**，通过适配器接入多个数据源，不绑定任何一家。

| 数据源 | 接入方式 | 适用阶段 | 说明 |
| --- | --- | --- | --- |
| 罗盘后台导出 | 运营在罗盘导出 Excel/CSV，客户端拖入导入 | 第一阶段 | 最稳妥，无接口和账号风险；按导出模板解析字段 |
| 第三方抖音数据服务 | 有正式授权的数据 API 或导出 | 第二阶段起 | 选型时确认数据来源合规、授权方式、覆盖字段和价格 |
| 抖店开放平台 | 官方 OAuth | 视情况 | 只能拿到自有抖店的数据，不覆盖全市场榜单 |
| 手动录入 | 粘贴商品或视频链接 | 始终可用 | 兜底 |

**不做罗盘页面的浏览器自动化或爬取。** 这和 TikTok 插件被风控是同一类风险：抓取需要登录运营自己的抖音或抖店账号，账号被处罚的成本远高于手动导出的时间。我没有查到罗盘面向第三方的全市场数据官方接口，若有，以抖音电商开放平台文档为准。

**数据模型新增三张表：**

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| dy\_products | 抖音商品 ID、类目、价格带、销量与 GMV 趋势、带货视频数、数据日期 | 按快照日期存，保留趋势 |
| dy\_videos | 视频 ID、关联商品、播放与成交指标、本地参考文件哈希 | 参考爆款的来源记录 |
| product\_mappings | 抖音商品 ↔ TK SKU、目标市场、上架日期、映射人 | 把两个市场的数据连起来 |

**它带来的第二个闭环：选品回测。** 有了 product\_mappings，就能把抖音侧信号（销量增速、带货视频数、价格带）和目标市场的实际表现放在一起，回答「抖音上什么特征的爆款，搬到印尼也能卖」。第一阶段只做看板，数据够了再做选品评分，作为运营选品时的排序参考。

参考爆款视频只下载到运营本地用于拆结构，不上传云端、不进成片，与素材库的 reference 标记规则一致。

## 桌面客户端

客户端选 **Wails v2（Go）+ React/TypeScript**，媒体管线用 Go 写成独立模块，与云端后端用同一种语言，小团队只维护一套技术栈，渲染逻辑也能在客户端和服务端之间复用。选 Wails 而不是 Tauri，是因为 Tauri 的后端必须是 Rust，Go 只能作为 sidecar 进程，多一层进程通信；团队如果没有 Rust 积累，Wails 更省事。已确定采用 Go 技术栈（Wails），Tauri 不再作为备选。

客户端内部分四个模块：

- **素材库**：导入商家自有实拍、商品图、参考爆款；按 SKU 组织，入库即触发切镜和打标。
- **工作台**：选商品和参考爆款 → 生成脚本 → 自动配镜 → 预览，运营在简易时间线里替换镜头、改字幕、改口播后再导出。
- **任务队列**：本地渲染并发数按硬件能力自动设定，支持断点续跑；所有任务状态上报云端。
- **发布绑定**：成片导出后显示成片 ID，运营发布后把视频链接贴回，或从店铺视频列表里点选匹配（见回流章节）。

本地依赖尽量做成单文件二进制，避免打包 Python：FFmpeg 静态构建随安装包分发；ASR 用 whisper.cpp（或调用云端 ASR）；切镜用 FFmpeg 的 scene 滤镜。本地存储用 SQLite 作缓存和离线队列，以云端为准。

硬件编码做三级降级：NVIDIA 用 NVENC，Intel 核显用 QSV，Mac 用 VideoToolbox，检测不到或编码失败时回退 libx264。首次启动跑一次 5 秒的编码自检，结果上报云端，便于排查客服工单。

运维基础设施从第一版就要有：自动更新（Wails 可接 go-selfupdate 或自建更新服务）、崩溃与错误日志上报（Sentry）、安装包代码签名（Windows 证书 + macOS 公证），否则杀毒软件拦截会成为最大的工单来源。

## 媒体处理流水线

流水线的核心约定是一份**时间线 JSON**：上游（AI 层）只产出 JSON，下游（渲染器）只消费 JSON。两边可以独立迭代、独立测试。

1. **入库预处理**（本地）：FFmpeg 统一转码为工作格式（如 1080×1920、30fps 代理文件），抽关键帧缩略图，scene 滤镜切镜，镜头元数据写入素材库。
2. **语音转写**：whisper.cpp 本地转写带词级时间戳；机器太弱时走云端 ASR。参考爆款的转写结果只用于拆结构，不进成片。
3. **镜头打标**（云端 AI 网关）：每个镜头抽 3 帧送视觉模型，返回镜头类型、主体、是否有文字/水印/人脸、画面质量分。
4. **装配**（云端 AI 网关）：脚本生成 + 镜头匹配，输出时间线 JSON（见下例）。
5. **音频合成**：TTS 生成每段口播，按实际音频时长回写 JSON 中各段的时长。
6. **渲染**（本地）：Go 渲染器把 JSON 翻译为一条 FFmpeg filter\_complex 命令：裁切、拼接、字幕（ASS，字体取自语言包；FFmpeg 的 libass 需带 HarfBuzz，才能正确排版泰文、阿拉伯文等复杂文字和从右到左语言）、配音与 BGM 混音、响度标准化（loudnorm）。
7. **质检**：成片与本租户历史成片做感知哈希比对，相似度过高时提示重做；检查字幕越界、静音段、黑帧。

时间线 JSON 示例（字段为建议，非最终定义）：

```json
{
  "output_id": "T01-SKU88-H03-V0012",
  "locale": "id-ID",
  "recipe": {"ref_video": "ref_5521", "hook_type": "pain_question", "structure": ["hook", "demo", "compare", "cta"]},
  "canvas": {"w": 1080, "h": 1920, "fps": 30},
  "segments": [
    {"role": "hook", "clip": "own_1203", "in": 2.1, "out": 5.0,
     "vo": {"text": "Kulit kusam terus walau sudah skincare?", "voice": "id_female_1"},
     "caption_style": "bold_yellow"}
  ],
  "bgm": {"track": "lib_0042", "gain_db": -18}
}
```

`recipe` 字段就是后面效果归因用的特征，生成时就写入，不需要事后补标。

## AI 层

所有模型调用经云端 **AI 网关**统一出口，客户端不直接持有模型密钥。网关负责：按租户计量扣点、模型路由与降级、提示词版本管理、调用日志（用于复盘哪版提示词产出的视频效果好）。网关可用 LiteLLM 起步，后续需要时再自研。

| 能力 | 做什么 | 首选方案 | 备选 / 降级 |
| --- | --- | --- | --- |
| 爆款拆解 | 读参考视频的转写 + 关键帧，输出结构骨架、钩子类型、卖点顺序、节奏 | 多模态 LLM（Claude Sonnet 级） | 纯文本转写 + 小模型 |
| 镜头打标 | 每镜头 3 帧，输出类型、主体、文字/水印、质量分 | 便宜的多模态模型（Haiku 级），批量调用 | 自部署 Qwen-VL 类开源模型 |
| 脚本生成 | 按骨架 + 商品卖点，直接用目标语言写口播，每段带时长上限 | Claude Sonnet 级，强约束 JSON 输出 | 同级其他模型 |
| 镜头匹配 | 为脚本每段从自有素材池选镜头 | 规则打分（类型匹配 + 质量分 + 近期使用次数）+ LLM 复核 | 纯规则 |
| 多语言 TTS | 口播合成 | 商用服务，按语言逐个盲测后定（候选：Azure 神经语音、ElevenLabs、Google Cloud TTS），不同语言可选不同供应商 | 真人配音上传通道 |
| ASR | 转写参考视频和素材原声 | whisper.cpp large-v3 本地 | 云端 ASR |
| 文字擦除（可选） | 擦除参考镜头里的中文字幕 | 第二阶段再评估：OCR 检测（复用内部 OCR 接口）+ 视频修复模型，部署在共享 GPU 服务器 | 不提供，提示换镜头 |

脚本生成是效果的关键，提示词里固定注入四类上下文：商品信息与卖点、参考爆款的结构骨架、目标市场的口语与带货话术样例、每段的时长上限。时长约束放在生成阶段，不做事后压缩语速，配音才自然。

TTS 选型用盲测决定：每新增一种语言，用同一批 10 段脚本让各候选合成，请 3–5 位该语言母语者打分，按语言分别选定供应商和音色。高价值 SKU 保留真人配音通道，客户端支持上传录音替换 TTS 段落。

### 多语言支持

语言按 locale 配置（如 id-ID、th-TH、vi-VN、ms-MY、en-PH），每个 locale 是一个**语言包**。新增市场只加语言包和做一轮 TTS 盲测，不改代码。

| 语言包内容 | 用途 |
| --- | --- |
| 提示词片段 | 口语风格、带货话术样例、禁用词与夸大宣传词表（各市场广告规范不同） |
| TTS 配置 | 供应商、音色、默认语速 |
| 字幕样式 | 字体（必须覆盖该文字）、每行字数上限、是否从右到左排版 |
| 语速系数 | 该语言每秒平均音节或字数，用来把时长上限换算成脚本每段的字数上限 |
| 本地化格式 | 货币、价格写法、促销用语 |

三条规则：

- **直接用目标语言生成，不从中文翻译。** 中文只作为运营的工作语言：工作台在每段口播旁显示回译中文，看不懂目标语言的运营也能审稿。
- **一套画面，多套语言。** 同一个 SKU 的画面轨可以复用，换配音和字幕生成各语言版本；但每个语言版本是独立的 output\_id，带 locale 字段，回流和归因按语言分开。
- **ASR 同样多语言。** Whisper 本身支持多语言识别，参考爆款和素材原声的转写不需要按语言换模型。

## 模型成本与计费

计费分两层：先做**内部成本核算**（每次模型调用都记账，算清单条成片成本），再做**对外点数计费**（多租户开放时）。第一阶段就要上线前者，否则无法定价，也发现不了成本失控。

**计量：** 所有调用必经 AI 网关，网关每次调用写一条 usage\_event。LiteLLM 自带按 key 和团队统计花费的能力，可直接作为起点，再落库到自己的表。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| usage\_events | tenant\_id、shop\_id、job\_id / output\_id、能力类型、供应商、模型、输入/输出/缓存 token、图片数、TTS 字符数、ASR 分钟、价格版本、成本、耗时、成功与否 | 只追加不修改，是所有成本分析的事实表 |
| model\_prices | 供应商、模型、计价单位、单价、生效日期 | 价格带版本，调用时按当时价格算成本，调价不影响历史 |
| tenant\_budgets | 租户/店铺日预算、月预算、告警阈值、硬上限 | 到 80% 告警，到上限暂停非必要调用 |
| credit\_ledger | 租户、点数变动、原因（充值/预扣/结算/退还）、关联任务 | 第四阶段启用，只追加的点数流水 |

**单条成片成本**按下式核算，参考爆款的拆解成本由所有引用它的成片分摊：

```latex
C_{\text{成片}} = \frac{C_{\text{拆解}}}{N_{\text{引用}}} + \sum_{\text{新镜头}} C_{\text{打标}} + C_{\text{脚本}} + C_{\text{TTS}} + C_{\text{重试}}
```

本地渲染和本地 ASR 不产生模型费用；只有本机太弱而改用云端 ASR 时才计入。第一阶段跑一批真实成片后，用 usage\_events 算出各项实际占比，作为定价依据，不先拍脑袋估数。

**降本手段（按收益排序）：**

- **模型分级：** 打标用 Haiku 级小模型，只有拆解和脚本用 Sonnet 级。
- **结果缓存：** 每个镜头只打标一次，标签随素材复用；同一参考爆款只拆解一次。
- **提示词缓存：** 系统提示词和语言包是固定前缀，开启供应商的提示词缓存。
- **批处理：** 入库打标不赶时间，走供应商的批处理接口（通常有折扣，以当前价格为准）。
- **限制重试：** 脚本重新生成次数设上限，超过后提示运营手动修改。

**对外点数计费（第四阶段）：**

- 点数与成本挂钩：各能力按点数定价（如每次脚本生成、每千字 TTS），点数单价 = 成本 × 目标毛利，供应商调价时只改点数表。
- 套餐 = 月费含一定点数 + 加购点数包。
- 生成前先显示预估点数；任务开始时**预扣**，完成后按实际结算多退少补，失败的任务全额退还。
- 商家后台可查每条成片花了多少点、花在哪个环节，减少计费纠纷。

## 云端后端与数据模型

后端用 **Go 单体**（按模块分包：账号、素材元数据、AI 网关、回流、分析），PostgreSQL 做主库，Redis 做队列和缓存，对象存储放缩略图和小文件。第一阶段不拆微服务，3–5 人团队维护单体最省力；回流同步这类定时任务用 River（基于 Postgres 的 Go 任务队列）或 Asynq（基于 Redis）。部署区域选新加坡，离印尼近、延迟低。

视频原文件**不上云**，只上传元数据和缩略图；需要云端 AI 处理时只传抽帧和音频片段。这是带宽和存储成本能压下来的关键。

从第一天起所有表带 `tenant_id`，并开启 PostgreSQL 行级安全（RLS），即使先只给朋友用，以后开放多租户不用重构。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| tenants / users / shops | tenant\_id、角色、店铺所属市场与默认 locale | 一个运营管多家店 |
| skus | 商品信息、类目、卖点（按 locale 存多语言版本） | 脚本生成的输入 |
| assets | 来源（自有实拍 / AI 生成 / 参考）、时长、本地路径哈希 | 参考类素材禁止进入成片 |
| clips | asset\_id、起止时间、标签、质量分、使用次数 | 镜头级索引 |
| references | 参考爆款、结构骨架 JSON | 只存结构，不存视频 |
| outputs | output\_id、locale、timeline JSON、recipe、感知哈希、prompt 版本 | 每条成片的完整配方 |
| publications | output\_id ↔ TikTok 视频 ID、店铺、发布时间 | 回流的主键桥 |
| ad\_accounts / oauth\_tokens | advertiser\_id、加密 token、scope | 用 KMS 或 age 加密存储 |
| metrics\_daily | 视频 ID、日期、曝光、点击、2s/6s 播放率、完播率、花费、订单、GMV | 回流事实表 |

数据量起来以后，metrics\_daily 可以同步一份到 ClickHouse 做分析；第一阶段 Postgres 足够。

## 发布绑定与效果回流

回流的主键是 **TikTok 视频 ID**，在发布环节绑定到成片 ID。不依赖文件名或广告名：视频上传后会被平台重新转码，文件哈希必变；GMV Max 投放的是已发布的商品视频，也不经过手工填广告名这一步。

**绑定方式（由弱到强，逐步上线）：**

1. 运营发布后把视频链接贴回客户端，系统解析出视频 ID 写入 publications 表。
2. 接 TikTok Shop Partner API 拉店铺视频列表，按发布时间、关联商品、时长自动给出候选，运营一键确认。Shop 侧的视频表现接口路径为 `analytics/202403/shop_videos/performance`（[参考](https://clawhub.ai/linkfox-ai/linkfox-tiktok-shop-analytics)），需在 Partner Center 建应用并完成店铺授权（[参考](https://pypi.org/project/tiktok-shop-mcp/)）。
3. 绑定只靠元数据匹配，不在视频画面里嵌水印或隐写编号，成片保持干净。

**数据来源：**

| 来源 | 接口 | 拿到什么 | 授权 |
| --- | --- | --- | --- |
| 广告（GMV Max） | Business API v1.3 `/gmv_max/report/get/`（[参考](https://support.fivetran.com/hc/en-us/community/posts/35557978705687-Connector-Improvement-TikTok-Ads-Connector-Add-GMV-Max-Creative-Level-Reporting-Video-Level-Sales-Detail)） | 素材级花费、订单、GMV、ROI、25/50/75/100% 播放率（[字段参考](https://docs.supermetrics.com/v1/docs/tiktok-ads-smart-ads-and-gmv-max-campaign-reporting-august-10-2026)） | 广告主 OAuth（[流程参考](https://docs.mintmcp.com/docs/tiktok-ads-mcp-setup)） |
| 广告（常规） | `/report/integrated/get/` | 非 GMV Max 广告的素材报表 | 同上 |

| 兜底 | 运营导入 Seller Center / Ads Manager 导出的 CSV | 任意字段 | 无 |

同步策略：每天定时拉过去 7 天数据覆盖写入（广告数据有归因回溯，近几天的数字会变）；按天查询注意 GMV Max 单次最多 30 天范围。所有拉取任务按租户、按广告主排队并遵守接口限流，token 加密存储，商家可随时在客户端解除授权。

## 效果分析与反哺生成

分析的目标是回答「哪种配方在哪个市场、哪个类目更好」，再把答案写回脚本生成和镜头匹配的默认值。

**指标分两层，分开评估：**

- **内容层**（衡量钩子和结构）：2 秒播放率、6 秒播放率、完播率、平均观看时长。受商品和价格影响小，适合比较配方。
- **转化层**（衡量商品和整体）：点击率、订单、GMV、ROI。受价格、库存、投放预算影响大，不直接拿来比较钩子。

**三个必须处理的偏差：**

1. **预算分配偏差。** GMV Max 会把预算集中给早期表现好的视频，多数视频曝光很少。设最低样本门槛（曝光或花费不足的视频不参与评分），评分用贝叶斯收缩（Beta-Binomial），小样本的比率向类目均值收缩。
2. **市场与语言混杂。** 按 locale + 类目分组评估，不同市场的数据不合并比较。
3. **时间混杂。** 大促、季节、商品生命周期会影响所有视频。比较同一时间窗口内发布的视频，或在模型里加时间固定效应。

**反哺方式（按阶段递进）：**

- 第一阶段：看板。按配方特征（钩子类型、结构、实拍占比、配音方式、时长）分组展示内容层指标，运营人工决定下一批怎么做。
- 第二阶段：推荐。生成脚本时，按 locale + 类目给出得分最高的 2–3 种钩子和结构作为默认选项，同时保留约 20% 的探索比例，避免只复制已知配方。
- 第三阶段起：素材评分作为投放模块的输入（优先给高分素材预算），投放结果再回到素材评分，见下一章。

多租户开放后，跨租户数据只用于匿名聚合的类目级结论（例如某类钩子在某类目的平均 6 秒播放率），需在服务条款中明确告知并取得同意，不展示任何具体商家的视频或数据。

## 投放与监控

投放和监控与回流共用同一份数据，接入后系统形成「选品 → 素材 → 投放 → 回流 → 优化」的完整闭环。全部走 Business API 官方接口，与浏览器插件是两回事：官方接口已支持创建 GMV Max 广告系列、获取出价建议等写操作（[参考](https://composio.dev/toolkits/tiktok_ads)），GMV Max 已在印尼、马来西亚、菲律宾、泰国、越南、新加坡、美国开放（[来源](https://ads.tiktok.com/help/article/how-to-create-a-product-gmv-max-campaign-in-tiktok-ads-manager)）。

**可控的杠杆有限。** GMV Max 由平台自动挑选商品、素材和版位，系统能动的是：日预算、目标 ROI、参投商品、喂给它的素材。预算修改还有当日次数和最小金额限制（[参考](https://ftp.fau.de/cran/web/packages/rtiktokads/refman/rtiktokads.html)），规则引擎必须读取并遵守。所以投放模块的价值在于三件事：持续供应好素材、按规则调预算与 ROI、及时发现异常。

**分三级上线，逐级放权：**

| 级别 | 做什么 | 所需权限 | 上线阶段 |
| --- | --- | --- | --- |
| 监控告警 | 每小时同步报表，规则命中即推送 | 只读（报表） | 第二阶段，与回流一起 |
| 建议 + 一键执行 | 系统给出调整建议，运营确认后执行 | 广告管理写权限 | 第三阶段 |
| 规则内自动 | 在店铺级边界内自动调整，越界仍需人工 | 同上 | 第四阶段 |

**首批监控规则（阈值由运营按店铺配置）：**

| 规则 | 触发条件 | 动作 |
| --- | --- | --- |
| 空烧 | 当日花费超过阈值且无订单 | 告警，建议降预算或暂停商品 |
| ROI 走低 | 连续 N 小时 ROI 低于目标 | 告警，建议换素材或调目标 ROI |
| 素材异常 | 视频被拒、被限流或违规 | 告警，提示从素材库补位 |
| 余额不足 | 广告账户余额低于预估 N 天花费 | 告警 |
| 发布限额 | 店铺近 7 天发布数接近平台限额 | 告警，提醒放缓发布 |
| 素材枯竭 | 某商品在投素材数低于下限，或主力素材播放率下滑 | 告警，在工作台生成补素材任务 |

最后一条把投放和素材生产连起来：投放端发现素材不够或疲劳，自动在工作台生成制作任务。

**动钱的操作，护栏先于功能：**

- 所有写操作进**审批队列**，记录发起方（规则或人）、调整前后数值、执行结果，形成完整审计日志。
- 每个店铺设边界：单日预算上限、单次调整幅度上限、ROI 下限；越界的动作一律转人工。
- 全局和店铺级「暂停自动化」开关，一键停止所有自动写操作。
- 自动执行上线前先**空跑**至少两周：只记录「系统会怎么做」，与运营实际决策对比，确认可靠再放权。
- 写操作失败或接口限流时不重试改值，只告警，避免重复调整。

**模块设计：** 云端新增规则引擎（定时任务读取最新报表，按规则产出告警或待执行动作）、动作执行器（只从审批队列取已批准的动作调用接口）、通知服务（飞书、企业微信或 Telegram 机器人，按运营习惯选；告警消息带一键跳转到客户端对应页面）。报表同步频率从每天提到每小时，按广告主排队并遵守接口限流。

**数据模型新增：** rules（规则定义与阈值，按店铺）、alerts（告警记录与处理状态）、ad\_actions（待审批与已执行的动作，含前后值）、shop\_guardrails（各店铺边界设置）。

## 合规与风控设计

合规不是附加功能，而是写进数据模型和流程的约束：TikTok Shop 已在 2025 年 9 月起加强处罚非原创和重复内容（[来源](https://www.bigseller.pro/blog/articleDetails/3778/tiktok-unoriginal-content.htm)），2026 年又加了发布限额（[来源](https://www.bigseller.pro/blog/articleDetails/4377/tiktok-shop-content-posting-limit-update.htm)）。产品要帮商家避开这些处罚，而不是绕过检测。

| 风险 | 系统内的约束 |
| --- | --- |
| 搬运他人视频 | 参考类素材在数据层标记为 reference，渲染器拒绝把它放进成片；成片中自有素材占比低于阈值时禁止导出 |
| 矩阵内重复 | 导出前与本租户历史成片做感知哈希比对，过近则提示重做；同一配方在多店发布时强制差异化（不同镜头组合和口播） |
| 发布频率触发限额 | 工作台按店铺显示近 7 天发布数，接近平台限额时提醒 |
| 夸大宣传 | 语言包内置各市场禁用词表，脚本生成后自动扫描，命中则标红并要求修改 |
| 账号风控 | 客户端不做任何浏览器自动化、模拟登录或代发；只走官方 OAuth 接口；写操作经审批队列、店铺边界和审计日志 |
| 授权数据安全 | token 加密存储、按租户隔离（RLS）、商家可随时解除授权、操作审计日志 |
| 音乐版权 | BGM 只用有商用授权的曲库，曲目带授权记录 |

对外开放前，还需准备公司主体、官网、服务条款、隐私政策，用于 TikTok 开发者应用审核；具体要求以审核时的官方说明为准。

## 风险与待验证事项

最大的风险是运营不愿意拍自有素材：如果商家坚持只用搬运素材，这套系统的原创性优势就不成立。第一阶段要先验证这一点。

- [ ] 运营每个 SKU 拍 10–20 个实拍镜头的成本能否接受（时间、是否需要样品）
- [ ] 新流程出片时间对比现在的 Codex 混剪流程，目标至少持平
- [ ] 新流程视频的违规率、限流率是否低于现有流程
- [ ] 各目标语言 TTS 盲测结果是否达到可用水平
- [ ] TikTok Business API 与 Shop Partner API 的申请主体、审核要求和所需 scope（以官方文档为准）
- [ ] GMV Max 素材级报表能否稳定按视频 ID 关联到成片
- [ ] 运营电脑硬件分布（显卡、内存、系统版本），决定本地渲染的降级策略
- [ ] 单条成片的 AI 调用成本（打标 + 脚本 + TTS），作为将来定价依据

* [ ] 罗盘导出文件的字段和格式是否稳定；第三方抖音数据服务的数据来源、授权方式和价格；Business API 广告管理写权限的申请要求，以及 GMV Max 预算、目标 ROI 修改接口的实际限制
